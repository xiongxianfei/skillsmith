# Change rationale

The old `specs/` tree combined long-lived obligations, successive editor amendments and historical test plans. The old architecture folder combined logical editor flow with responsibility and implementation detail. A folder rename would leave readers uncertain which editor language/learning rule applies. The user's selected design layout now gives each kind of knowledge one owner.

Requirements retain observable contracts, examples and acceptance. System documents explain logical Functions and reusable proof intent. Architecture allocates responsibility and Interfaces to the existing portable prompts, checks and reviewers, separately from maintenance tooling. The editor contract consolidates only explicit amendments and keeps source-qualified inherited fidelity, precision, ambiguity, learning-label and safety constraints. No product prompt was changed to make documentation pass.

Exact source snapshots and hashes preserve prior evidence, including previously uncommitted reviewed drafts. Historical test plans stay with their original changes; they are not new execution results. The clause/block dispositions make preservation inspectable, and negative tests demonstrate the audit detects missing evidence or retained content. Historical navigation is labeled, without rewriting old approval claims into current ones.

Governance, contributor guidance and project-map navigation now agree on the three roots and the reviewed RigorLoop v2 process. Optional metadata guidance follows the constitution; the vision's contradictory mandatory argument hint and stale fixed catalog counts are removed. The user's engineering principles remain byte-identical.

The tracked project UUID and ignored runtime directory support maintainer coordination. The pinned CLI/runtime and recovery guide keep setup reproducible; the disposable fixture proves the documented preview/stale-update/backup/restore behavior. This adoption remains under the existing governance until acceptance/merge and does not fabricate managed records for earlier isolated work.

[Implementation evidence](implementation-evidence.md) provides actual checks and limitations. [Upstream reviews](reviews/design-review.md) explain old-to-new gate coverage; whole-change review and final verification assess the delivered candidate separately. No PR, merge, hosted CI result or model-quality result is implied by local completion.
